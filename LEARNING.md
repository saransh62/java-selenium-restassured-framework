# Learning guide

A walkthrough of the code in the order that makes it easiest to understand, followed by likely interview questions.

## Reading order

1. **`pom.xml`**: dependencies and the Surefire setup. Note the `-javaagent` AspectJ weaver (makes Allure `@Step` work) and `${suite}`, which selects the TestNG XML.
2. **`src/test/resources/config.properties`** → **`config/ConfigManager`**: where every setting comes from and how `-D` overrides it.
3. **`driver/DriverFactory`**: `ThreadLocal<WebDriver>`, browser options, local vs `RemoteWebDriver`.
4. **`pages/BasePage`**: waits, `click()` with intercept fallback, `handlePopups()`. Every page inherits this.
5. **One simple page + test**: `pages/HomePage` → `ui/HomePageTest`. See how a test only expresses intent.
6. **`test/base/BaseUiTest`**: browser lifecycle and API-driven user setup/cleanup.
7. **The rest of the pages**, following a user journey: `SignupLoginPage` → `AccountCreatedPage` → `ProductsPage` → `ProductDetailPage` → `CartPage`/`CartItem` → `CheckoutPage`; then `ContactUsPage`.
8. **UI tests**: `AuthTest` (data-driven invalid logins), `ProductsTest`, `CartTest`, `CheckoutTest`, `ContactUsTest`.
9. **API layer**: `api/ApiClient` (shared spec + filters) → `api/ApiResponse` (the `responseCode` quirk) → `ProductsClient`, `BrandsClient`, `AccountClient` → `api/models/*`.
10. **API tests**: `BaseApiTest` (schema helper) → `ProductsApiTest`, `BrandsApiTest`, `AccountApiTest`; schemas in `src/test/resources/schemas`.
11. **`hybrid/HybridTest`**: how API and UI combine.
12. **`utils`**: `TestDataFactory` (unique data), `JsonDataReader` (data providers), `ScreenshotUtil`.
13. **`listeners`**: `TestListener` (evidence on failure + retry wiring), `RetryAnalyzer`; registered via `src/test/resources/META-INF/services`.
14. **Suites**: `testng.xml`, `smoke.xml`, `regression.xml`, `api.xml`, `ui.xml`.
15. **Infra**: `docker-compose.yml` (Grid), `.github/workflows/ci.yml` (CI + Allure on Pages).
16. **`DESIGN.md`** for the reasoning.

## Interview questions

**1. How does the framework run tests in parallel safely?**
`parallel="methods"` with 4 threads. Each thread gets its own `WebDriver` via `ThreadLocal`, each test gets a fresh browser, and test data is unique per test (`TestDataFactory`). Shared objects (config, base request spec) are immutable.

**2. Why `ThreadLocal` instead of a static driver or passing the driver around?**
A static driver is shared across threads and breaks under parallelism. Passing it everywhere is noisy. `ThreadLocal` gives every thread its own instance with a global accessor (`DriverFactory.getDriver()`), which listeners can also use to take screenshots of the right browser.

**3. Explicit vs implicit waits, and why no `Thread.sleep`?**
Explicit waits poll for a specific condition and continue as soon as it is true. Implicit waits apply globally to every `findElement` and interact badly with explicit waits. `Thread.sleep` always waits the full time, so it is slow when the page is fast and still flaky when it is slow.

**4. How do you handle ads and popups?**
`BasePage.handlePopups()` accepts consent if shown, reloads without the `#google_vignette` hash, and removes ad iframes/containers via JavaScript. `click()` falls back to a JS click if an overlay intercepts it. All of it is best-effort and cannot fail a test.

**5. This API always returns HTTP 200. How do you assert status?**
`ApiResponse` parses the body as JSON regardless of the `text/html` content type and exposes `responseCode()`. Tests assert on that and on `message`.

**6. What is the hybrid approach and why use it?**
Use the API for setup, cleanup and as a source of truth, and the UI only for the behaviour under test. Example: create a user via API, log in via UI, verify the header, delete via API. It makes UI tests faster and less flaky, and checks UI and backend agree.

**7. How is test data managed?**
Static data (search terms, invalid logins, contact form) lives in JSON under `testdata/` and is fed through `@DataProvider` via `JsonDataReader`. Dynamic data (users) is generated by `TestDataFactory` with unique emails, and cleaned up after each test.

**8. How does the retry mechanism work and why only for UI?**
`RetryAnalyzer` retries once. `TestListener.transform()` attaches it only to classes extending `BaseUiTest`. UI tests depend on a live site with third-party ads; API tests are deterministic, so retrying them would hide real bugs.

**9. What happens when a UI test fails?**
`TestListener.onTestFailure` runs before `@AfterMethod`, so the browser is still open; it attaches a screenshot, page source and URL to Allure.

**10. How do you switch between local, Grid and browsers?**
Config flags: `-Dbrowser=firefox`, `-Dheadless=false`, `-DgridUrl=http://localhost:4444`. `DriverFactory` builds a local driver or `RemoteWebDriver` from the same options.

**11. How do you validate API contracts?**
JSON Schema files in `src/test/resources/schemas` validated with REST Assured's `matchesJsonSchemaInClasspath` against the raw body. They check types, required fields and formats (e.g. price `^Rs\. \d+$`) independently of data values.

**12. Why Selenium Manager instead of WebDriverManager?**
It ships with Selenium 4.6+, resolves matching drivers (and browsers if needed) automatically, and removes a third-party dependency.

**13. What does the AspectJ weaver do?**
Allure's `@Step` annotations are implemented with AspectJ. The weaver, loaded as a Java agent in Surefire, intercepts annotated methods at runtime so each page/client call appears as a step in the report.

**14. How does CI work?**
Two parallel jobs: API tests on the runner, UI + hybrid tests against a `selenium/standalone-chrome` service container. Both upload Allure results; on pushes to `main` a third job merges them, restores history from `gh-pages` and publishes the report to GitHub Pages.

**15. What would you improve next?**
Run the cross-browser matrix in CI (Firefox job), add API-driven cart setup if the API exposed one, tag tests with Allure `@Severity`/`@Story`, add a test-data cleanup sweep for interrupted runs, and introduce a typed config object instead of string keys.
